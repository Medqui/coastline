# Supabase setup

1. Create a Supabase project and configure Auth email sign-in.
2. For CLI installs, link your project and run `supabase db push`. Migrations 006 and 008–018 tolerate the supported previously installed objects, including SQL Editor installs not yet recorded in CLI history. The complete current migration sequence can be replayed without changing stored hotel records. For SQL Editor installs, run the **whole** `supabase/repeatable-install.sql` file. It installs or upgrades migrations 000–018 in one transaction, tracks its checksum, and makes subsequent runs of the same release a no-op. It rejects a recorded newer/different release rather than downgrading it. Use the latest generated installer; older exported bundles may not have replay protection.
3. Copy `.env.example` to `.env.local` and set the Supabase project URL and publishable key. Never put the service-role key in this app's browser environment.
4. Restart `npm run dev`, sign up, verify the email if confirmation is enabled, then sign in. The app will send a user without a hotel membership to `/onboarding`.
5. Set up the organization, property, room count and standard nightly rate. The setup transaction creates the owner membership and rooms.
6. Housekeeping marks a room clean or inspected. Front desk can then create a reservation and check the guest in on the arrival date. Open the folio to post completed room nights, extras, and payments. Finance staff can post paid expenses. On or after departure, settle the folio and check out the guest.

All tenant-owned tables have RLS enabled. App writes use authenticated, role-checked database functions rather than broad browser insert/update permissions. Reservation creation serializes by room and rejects overlapping confirmed stays. Check-in verifies the current property-local date and room readiness.

The finance migrations seed a chart of accounts and payment methods, post balanced double-entry journals for room nights, extras, payments, paid expenses, deposits, deposit applications, and refunds, and lock posted journals against edits. Owner figures come from posted entries. Reservation totals remain quotes until room charges post. Advances are liabilities until applied to charges. Owners and managers may refund unapplied deposits or regular payments on an open folio with a reason.

**Current limits:** Reservations still contain one room. Team invitations create a secure, seven-day, property-scoped link for the owner to share manually; email delivery is not configured. Bank statements import from CSV rather than direct bank feeds. Matching is one statement line to one posted ledger movement with the exact signed amount; exceptions remain open until the missing or incorrect ledger entry is resolved. Backups and restore drills are described in `docs/operations-runbook.md` and must be configured in the Supabase project. Refunds remain limited to payments on an open folio; unapplied deposits must be applied or refunded before checkout.

Migration 014 accepts CSV headers `date,description,reference,amount,balance`, where receipts are positive and payments are negative. It also accepts separate `debit` and `credit` columns. Dates may be `YYYY-MM-DD` or `DD/MM/YYYY`. Imports are immutable and idempotent; a reconciliation using imported lines cannot complete until every statement line and every posted movement for the selected account and period is matched.

Apply migrations 008 and 009 before running the updated booking and room-management screens. These add owner/manager approval for rate overrides and maintenance blocking. The migration bundle in task outputs contains both updates in one transaction.

Then apply migration 010 for date-effective prices, nightly booking snapshots and nightly posting. It preserves historical agreed amounts; it does not reprice old reservations. The current booking form requires the nightly quote RPC and nightly snapshot relation from this migration.


## Repeatable installation and verification

The repeatable installer is generated by `python3 scripts/build-repeatable-installer.py`. Regenerate it after a reviewed migration change; its checked-in output must match the generator. CLI history remains managed by `supabase db push`. The installer uses a separate administrator-only release marker and does not forge CLI migration history. If SQL Editor was used first, a subsequent CLI push can now apply/record the missing known migrations safely.

`python3 scripts/test-migration-replay.py` requires a migrated disposable **local** database with no hotel organizations. It seeds real operations and finance facts, replays the complete versioned sequence, applies the installer twice, and checks exact stored-record preservation and pricing permissions. It rolls back fixtures and every replay operation. Run it before `scripts/test-booking-concurrency.py`, which leaves its synthetic fixtures for inspection. CI follows that order. Hosted migration execution and browser acceptance are recorded separately from local integration evidence.
